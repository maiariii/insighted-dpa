# Fullstack Shadcn Architect

## Core Workflow
1. Define the feature contract before editing code.
2. Implement backend changes by module with strict layer boundaries.
3. Implement frontend changes by feature slice with shadcn/ui primitives.
4. Integrate via a single feature service and explicit UI states.
5. Validate with anti-spaghetti checks before finalizing.

## Step 1: Define the Contract
- Capture endpoint path, method, request body, response body, and error codes first.
- Map required UI states: idle, loading, success, empty, validation error, and server error.
- Use [fullstack-contract-template.md](references/fullstack-contract-template.md) as the source of truth before coding.

## Step 2: Implement Backend With Layered Boundaries
- Read [backend-layered-patterns.md](references/backend-layered-patterns.md) before touching backend files.
- Keep flow strictly `route -> controller -> service -> repository`.
- Keep controllers thin: translate HTTP input/output only.
- Keep services focused on business rules and orchestration.
- Keep repositories focused on data access and external I/O.
- Keep validation at route boundary using request schemas.
- Keep domain errors in service/repository, then map to HTTP status in controller or error middleware.

## Step 3: Implement Frontend With shadcn/ui
- Read [frontend-shadcn-patterns.md](references/frontend-shadcn-patterns.md) before touching frontend files.
- Keep `src/components/ui/*` as reusable primitives generated by shadcn CLI.
- Keep feature-specific behavior under `src/features/<feature>/`.
- Keep pages and routes thin by composing feature containers and ui primitives.
- Keep data loading and mutation in hooks/services, not inside presentation components.

## Step 4: Integrate Frontend and Backend Cleanly
- Keep one client service per feature for HTTP calls.
- Keep API response shaping in hooks or mappers before rendering.
- Keep retry/toast/error handling consistent across all feature entry points.
- Keep naming consistent across database fields, API keys, and UI labels.

## Step 5: Run Anti-Spaghetti Checks
- Read [anti-spaghetti-checklist.md](references/anti-spaghetti-checklist.md) and pass all blocking checks.
- Reject mixed-responsibility files and hidden cross-layer imports.
- Prefer small, composable files over large catch-all modules.

## Output Contract
Return results in this order unless user asks otherwise:
1. Feature contract summary.
2. Proposed file tree changes.
3. Backend changes grouped by route/controller/service/repository.
4. Frontend changes grouped by pages/features/ui/services.
5. Validation results and residual risks.
